# Правила работы Codex в этом проекте

Главная цель: **максимально экономить токены, время и количество действий без потери качества, корректности и безопасности результата**.

Приоритеты в таком порядке:

1. корректность и юридическая безопасность;
2. выполнение задачи пользователя;
3. минимальный объём изменений;
4. минимальный расход токенов и вычислений.

Экономия токенов никогда не является основанием пропускать необходимую юридическую, логическую или техническую проверку.

## Рабочий режим по умолчанию

1. Сначала пойми точную цель задачи и критерий готовности.
2. Найди **минимальный набор файлов**, влияющих на задачу.
3. Читай только нужные участки файлов, а не весь проект целиком.
4. Составь короткий план из 2–4 пунктов только если задача не тривиальна.
5. Внеси минимально достаточные изменения.
6. Проверь результат самым дешёвым надёжным способом.
7. Как только критерий готовности выполнен — остановись.

Не выполняй дополнительную работу «заодно».

## Экономия контекста и поиска

- Не сканируй весь репозиторий без явной необходимости.
- Начинай с точного поиска по имени файла, маршруту, символу, функции, компоненту или тексту ошибки.
- Ограничивай поиск несколькими наиболее релевантными результатами.
- Расширяй область поиска только если первый точечный поиск не дал ответа.
- Не открывай повторно неизменённый файл, если нужная информация уже есть в текущем контексте.
- Не перечитывай большие файлы целиком ради одного символа или небольшого блока.
- По возможности объединяй связанные чтения и проверки в один шаг.
- Не повторяй команды, результаты которых уже известны и остаются актуальными.
- Не пересказывай пользователю содержимое файлов, если это не требуется задачей.

Каждый вызов инструмента или команды должен отвечать на конкретный вопрос: **«Какое решение я приму по результату этого действия?»** Если ответа нет — действие не выполняй.

## Изменения кода

- Меняй только то, что необходимо для текущей задачи.
- Не делай рефакторинг рабочего кода без прямой необходимости.
- Не меняй архитектуру, нейминг, форматирование, зависимости или структуру проекта ради «улучшения».
- Не обновляй зависимости и lock-файлы без необходимости.
- Не трогай соседние модули, если исправление можно сделать локально.
- Сохраняй существующие паттерны проекта вместо создания новых абстракций.
- Если есть несколько корректных решений, выбирай самое простое, локальное и легко проверяемое.

## Лестница проверок

Всегда используй **минимально достаточный уровень проверки** и повышай его только при необходимости.

1. Локальная логическая/синтаксическая проверка изменённого участка.
2. Targeted-тест конкретного модуля, функции, маршрута или генератора.
3. Typecheck/lint только затронутой области, если это возможно.
4. Более широкий набор тестов — если изменение влияет на несколько модулей или общую инфраструктуру.
5. Полный `typecheck`, `lint`, `build`, SEO/smoke или полный test suite — только если:
   - это прямо требуется задачей;
   - изменение затрагивает shared/core архитектуру;
   - готовится финальный acceptance/merge/release;
   - локальная проверка не даёт достаточной уверенности.

Не запускай полный production build после каждого небольшого изменения.

## Правила для ПравоПоиска

Для юридически значимых данных экономия контекста не должна снижать качество проверки.

Нельзя предполагать или выдумывать:

- нормы закона;
- сроки;
- госпошлины и тарифы;
- подсудность;
- полномочия органов;
- обязательные реквизиты;
- официальные формы;
- способы подачи;
- ссылки на официальные источники.

Если задача требует актуальной юридической проверки — используй только необходимый набор официальных источников и проверяй ровно те положения, которые влияют на изменение.

Не исследуй законодательство «на всякий случай» и не расширяй legal research за пределы поставленной задачи.

Если надёжно подтвердить юридически значимый факт нельзя — не угадывай; сохрани безопасный fallback (`CHERNOVIK`, `requiresLegalReview`, `filingReady=false` или иной уже используемый механизм проекта).

## Когда нужно остановиться и уточнить

Не задавай вопрос, если разумное минимальное предположение позволяет безопасно выполнить задачу.

Задай один конкретный вопрос только если неопределённость:

- может привести к неправильному пользовательскому поведению;
- меняет юридический результат;
- меняет публичный API/архитектуру;
- может затронуть production-данные;
- делает несколько вариантов решения существенно разными.

## Формат ответа после работы

Отвечай максимально кратко. Не публикуй внутренние рассуждения, длинные логи и пересказ процесса.

Достаточно сообщить:

- что изменено;
- какие файлы затронуты;
- какие проверки выполнены и их результат;
- риски/допущения — только если они реально есть.

Если всё выполнено и рисков нет — так и скажи одной короткой фразой.

## Критерий эффективности

Оптимальная работа Codex в этом проекте — не минимальное количество токенов любой ценой, а **минимальное количество токенов, действий и изменений, необходимое для надёжного выполнения задачи**.
