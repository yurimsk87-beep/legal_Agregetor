# SEO_ACCEPTANCE_RULES.md

Статус: **канонические SEO-правила проекта ПравоПоиск**  
Актуальность источников проверена: **2026-09-29**

Этот файл определяет правила индексации, технического SEO, контентного качества и поискового представления для публичных страниц ПравоПоиска.

Он имеет приоритет над устаревшими локальными эвристиками в коде, если они противоречат актуальным официальным рекомендациям Google Search Central и Яндекс Вебмастера.

Для Q&A дополнительно обязательны правила `QNA_CONTENT_RULES.md`. SEO-допуск Q&A не отменяет originality/legal/privacy gates.

---

## 1. Иерархия источников и запрет на выдуманные SEO-факторы

При принятии SEO-решений использовать источники в таком порядке:

1. актуальная официальная документация Google Search Central;
2. актуальная официальная документация Яндекс Вебмастера;
3. официальная документация Schema.org — только для значения типов/полей, но не как доказательство поддержки rich result конкретным поисковиком;
4. наблюдаемая практика сильных сайтов юридической тематики — только как пример реализации, а не как доказательство ranking factor.

Нельзя объявлять SEO-фактором или обязательным gate то, что поисковые системы официально не подтверждают.

В частности, нельзя считать самостоятельным ranking requirement:

- фиксированный объём текста;
- фиксированное число FAQ;
- фиксированное число внутренних ссылок;
- наличие CTA;
- наличие любого JSON-LD «ради JSON-LD»;
- значение внутреннего `seoScore`;
- ровно один H1 как требование Google;
- наличие `llms.txt`;
- искусственное обновление даты;
- процент «текстовой уникальности» сам по себе.

Внутренние эвристики допустимы для редакционного контроля, но должны быть явно обозначены как внутренние, а не как требования Google/Яндекса.

## 2. Базовый принцип индексации

Страница получает `index` только если одновременно:

```text
technicalIndexability = PASS
contentValue = PASS
duplicateCanonical = PASS
legalTrust = PASS        # если юридически значимый контент
privacy = PASS
pagePurpose = PASS
```

Дополнительные улучшения вроде structured data, OpenGraph, FAQ, CTA, цены, карточек юристов и т. п. сами по себе не делают страницу индексируемой.

Если основной контент слабый, дублирующий, устаревший или не решает задачу пользователя, наличие schema/canonical/sitemap не является основанием для индексации.

## 3. People-first content вместо «SEO-текста»

Google рекомендует создавать helpful, reliable, people-first content и прямо указывает, что у него нет предпочтительного количества слов. Яндекс отдельно считает нарушением SEO-тексты, добавленные ради ключей или объёма без дополнительной пользы.

Поэтому:

- поле/понятие `seoText` не должно использоваться как доказательство качества;
- пороги вида `>= 1500 символов` не являются SEO-gate;
- текст не дописывается ради длины;
- ключевые слова не повторяются искусственно;
- автоматический рерайт не считается ценностью;
- основной критерий — решает ли страница задачу пользователя лучше, понятнее и надёжнее.

Допустимо иметь короткую страницу, если она полностью решает узкую задачу.

Для сложной юридической ситуации допустим длинный материал, если длина обусловлена содержанием, а не SEO-порогом.

## 4. Юридический контент: trust, author, reviewer, freshness

ПравоПоиск работает с юридическими вопросами, которые могут существенно влиять на права, деньги, сроки и решения пользователя. Для таких материалов требуется усиленный trust layer.

Для юридически значимых страниц должны быть доступны, когда применимо:

- автор;
- юридический reviewer;
- профиль автора/reviewer;
- дата последней фактической юридической проверки;
- дата существенного обновления;
- ссылки на первичные или официальные правовые источники;
- указание региона/юрисдикции, если от неё зависит ответ.

Дата `updatedAt` не должна автоматически означать «юридически проверено».

Нельзя менять дату только для создания эффекта свежести.

Если закон изменился, а контент не перепроверен, страница должна переходить в состояние review/noindex в соответствии с внутренней моделью freshness.

### Проверенная практика legal-сайтов

Наблюдение, а не самостоятельный ranking factor:

- Nolo на юридических материалах показывает автора/редактора, дату обновления, блок `Why Trust Us / Fact-Checked` и редакционные стандарты.
- FindLaw показывает `By`, `Legally reviewed by`, `Last updated`, `Legally Reviewed`, `Fact-Checked`.
- Justia связывает публичные ответы с проверяемыми профилями адвокатов/юристов и их областями практики.

Эти паттерны совпадают с официальной рекомендацией Google явно показывать **Who / How / Why** и точное авторство там, где пользователь его ожидает.

Для ПравоПоиска это означает: юридический reviewer и дата проверки должны быть реальными данными продукта, а не декоративной подписью.

## 5. Originality, scaled content и импортированный Q&A

Массовое количество страниц само по себе не запрещено.

Запрещён риск-моделью проекта следующий сценарий:

```text
чужой Q&A
→ очистка
→ новый заголовок
→ лёгкий рерайт
→ index
```

Google относит массовый неоригинальный контент без дополнительной ценности к scaled content abuse / abusive scraping. Яндекс считает скопированный или минимально переработанный контент без дополнительной ценности малополезным.

Поэтому для импортированного Q&A обязательно действует `QNA_CONTENT_RULES.md`:

- originality gate;
- semantic duplicate gate;
- legal gate;
- privacy gate;
- quality gate.

Только формальная текстовая уникальность недостаточна.

## 6. Programmatic SEO, города и защита от doorway pages

Страницы вида:

- услуга × город;
- ситуация × город;
- юрист × город;
- тема × регион;

нельзя массово индексировать только потому, что комбинация URL существует.

Google прямо относит к doorway abuse множество похожих региональных/городских страниц, которые создаются для похожих запросов и ведут пользователя к одному и тому же конечному результату.

Индексируемая локальная/programmatic страница должна иметь самостоятельную ценность, например:

- реальный спрос;
- реальные релевантные исполнители;
- локально отличающиеся сведения;
- локальные цены/условия, если они реальны;
- юрисдикционные различия;
- собственный полезный контент;
- самостоятельные внутренние связи;
- отсутствие почти полного совпадения с другими городскими страницами.

Если страница отличается только названием города в шаблоне, она не должна автоматически становиться `index`.

Порог количества юристов, FAQ или символов может оставаться внутренней продуктовой эвристикой, но не заменяет проверку самостоятельной ценности.

## 7. Title, description и H1

### Title

Title должен:

- точно описывать страницу;
- соответствовать основному intent;
- не быть набит ключевыми словами;
- отличаться от других страниц, когда страницы действительно различаются;
- не обещать функциональность, которой нет.

Пример: фраза «заполнить онлайн и скачать» разрешена только если пользователь действительно может заполнить и скачать документ.

### Meta description

Meta description должна быть специфична для страницы и полезна пользователю.

Нет обязательной фиксированной длины, гарантирующей показ: Google может сформировать snippet из содержимого страницы.

### H1

ПравоПоиск сохраняет внутренний стандарт:

```text
одна страница → один основной H1
```

Это правило поддерживаемости, UX и семантической структуры проекта, но его нельзя описывать как подтверждённый Google ranking factor.

## 8. Internal linking и отсутствие orphan pages

Google прямо рекомендует, чтобы на каждый важный URL ссылалась хотя бы одна другая страница сайта.

Поэтому:

- индексируемая страница не должна быть orphan page;
- ссылки должны быть реальными `<a href>`;
- anchor должен описывать целевую страницу;
- бессмысленные `Подробнее`, `Нажмите здесь` не должны быть основным способом внутренней перелинковки;
- внутренние ссылки должны вести на canonical URL;
- нельзя вводить искусственный SEO-порог «минимум 3 ссылки».

Для ПравоПоиска предпочтительная смысловая граф-связь:

```text
Q&A ↔ жизненная ситуация ↔ документ/инструмент ↔ профиль юриста ↔ релевантная статья
```

Связь добавляется только если она реально полезна пользователю.

---

## 9. Внешние правовые источники

Google прямо указывает, что уместные внешние ссылки могут помогать формировать доверие к материалу.

Для юридического контента ПравоПоиска:

- при необходимости ссылаться на официальный первичный источник;
- не прятать источник только внутри JSON-LD;
- ссылку сопровождать понятным контекстом;
- не использовать `nofollow` для каждого официального источника автоматически;
- `nofollow` использовать, если источник не заслуживает доверия;
- оплаченные ссылки помечать `sponsored`;
- пользовательские внешние ссылки — `ugc` или `ugc nofollow`.

---

## 10. UGC/Q&A: noindex до доверия и rel=ugc

Google отдельно рекомендует для UGC-платформ:

- модерировать подозрительные публикации;
- не давать новым/недоверенным публикациям автоматически попадать в индекс;
- пользовательские внешние ссылки помечать `rel="ugc"` или `nofollow`.

Для ПравоПоиска это уже должно реализовываться через Q&A gates:

```text
created != indexable
published != indexable
moderated != automatically indexable
```

`isIndexable=true` — отдельное решение после gates.

## 11. Pagination — не путать с фильтрами

Настоящая пагинация и фильтры — разные сущности.

### Настоящая пагинация

Для последовательности вроде:

```text
/questions/?page=1
/questions/?page=2
/questions/?page=3
```

Google рекомендует:

- отдельный URL для каждой страницы;
- crawlable `<a href>` между страницами;
- каждая страница имеет собственный canonical;
- нельзя canonical'ить страницу 2/3/... на страницу 1 только потому, что это pagination;
- `rel=next/prev` Google больше не использует как сигнал пагинации.

Следовательно, глобальное правило:

```text
page > 1 => noindex
```

нужно считать устаревшим и убрать.

### Фильтры и сортировки

URL вроде:

- `?sort=`
- `?price=`
- `?rating=`
- `?online=`
- `?filter=`

обычно не должны создавать новые индексируемые версии одной и той же выдачи, если нет отдельного поискового intent и самостоятельной ценности.

## 12. Robots.txt, noindex и параметры

Критическое правило:

**если Googlebot заблокирован через robots.txt, он может не увидеть `noindex`.**

Поэтому нельзя проектировать удаление URL из индекса как:

```text
Disallow + noindex
```

с ожиданием, что Google обязательно прочитает `noindex`.

Использовать:

- `robots.txt` — для управления crawling;
- `noindex` — для исключения доступной роботу страницы из индекса;
- password/auth — для реально приватного контента;
- `rel=canonical` — для консолидации дублей;
- 301 — для постоянного переноса;
- 404/410 — когда ресурса действительно нет.

### Для Яндекса

Для параметров, которые не меняют содержимое, использовать `Clean-param`, где это применимо.

Яндекс прямо рекомендует `Clean-param` вместо `Disallow` для незначащих параметров, поскольку это помогает передавать сигналы основному URL.

UTM/analytics parameters не должны порождать отдельные индексируемые страницы.

## 13. Canonical

Canonical решает задачу выбора основной версии среди дублей/почти дублей.

Canonical **не является**:

- originality gate;
- quality gate;
- legal gate;
- гарантией индексации.

Правила:

- canonical URL должен быть абсолютным и валидным;
- основная страница должна иметь self-canonical;
- внутренние ссылки должны по возможности вести на canonical;
- sitemap содержит canonical URL;
- нельзя одновременно давать противоречащие canonical signals;
- для удалённой копии предпочтителен 301, если есть однозначная замена.

Google считает redirect и `rel=canonical` сильными сигналами, а sitemap — более слабым canonical signal.

## 14. Sitemap

### Общие правила

В sitemap включаются только URL, которые мы реально считаем canonical и хотим индексировать.

Не включать:

- `noindex`;
- duplicates;
- redirect URLs;
- 404/410;
- технические query variants;
- страницы, не прошедшие обязательные gates.

### Лимиты

Каждый sitemap:

- максимум 50 000 URL;
- максимум 50 MB uncompressed.

Большой Q&A должен автоматически разбиваться:

```text
sitemap-questions-1.xml
sitemap-questions-2.xml
...
```

и подключаться через sitemap index.

### lastmod

Использовать `lastmod` только когда дата отражает **последнее существенное изменение** контента/structured data/значимых ссылок.

Не менять `lastmod` ежедневно без реального изменения.

### changefreq и priority

Google игнорирует `changefreq` и `priority`.

Яндекс поддерживает эти поля как необязательные сигналы; `priority` может использоваться для порядка обхода внутри сайта, но это не нужно трактовать как ranking factor.

Следовательно:

- не выставлять blanket `weekly` всем страницам;
- `priority` оставлять только при осознанной стратегии для Яндекса;
- основной сигнал свежести — достоверный `lastmod`.

## 15. HTTP status и soft 404

Страница без реального контента не должна возвращать `200 OK` только потому, что route существует.

Правила:

- отсутствует ресурс → 404;
- ресурс окончательно удалён без замены → 404 или 410;
- есть явная постоянная замена → 301;
- пустая категория/поиск/карточка не должны маскироваться под полноценную индексируемую страницу;
- DB error не должен превращаться в индексируемую пустую страницу.

Google отдельно рассматривает страницы с сообщением «ничего нет» и HTTP 200 как возможные soft 404.

## 16. Structured data: только поддерживаемое и правдивое

Structured data:

- должна соответствовать видимому содержимому;
- не должна описывать то, чего пользователь не видит;
- не должна содержать выдуманные рейтинги, адреса, отзывы, авторов или услуги;
- не является прямым ranking factor;
- не гарантирует rich result.

Не использовать наличие любого JSON-LD как обязательный SEO score.

### FAQPage

С **15 июня 2026** Google удалил документацию FAQ rich result, потому что FAQ rich result больше не показывается в Google Search.

Следовательно:

- `FAQ >= 3` не является SEO-gate;
- `FAQPage` не является обязательным markup для Google;
- FAQ-блок остаётся только там, где он полезен человеку;
- существующий FAQ не надо удалять только из-за Google, если он полезен пользователю;
- отсутствие FAQ не должно блокировать индексацию.

Яндекс прямо говорит, что semantic markup может сделать результат заметнее, но напрямую не влияет на ранжирование.

### WebSite / SearchAction

`WebSite` можно сохранять для site-name и понимания сайта.

`SearchAction`, добавленный только ради Google Sitelinks Search Box, больше не нужен: Google прекратил поддержку этого элемента 21 ноября 2024 года.

## 17. QAPage — оставить и использовать строго корректно

Google и Яндекс продолжают поддерживать Q&A-разметку.

Для `QAPage`:

- страница посвящена одному вопросу;
- пользователь должен иметь возможность добавлять альтернативные ответы;
- весь текст question/answer в markup соответствует видимому контенту;
- `answerCount` соответствует реальному числу ответов;
- первый или самый новый ответ нельзя автоматически объявлять `acceptedAnswer`.

`acceptedAnswer` разрешён только если ответ действительно выбран:

- автором вопроса;
- модератором;
- системой голосования;
- иным явно определённым механизмом.

Если такого механизма нет — использовать `suggestedAnswer`.

### Author entity

Для ответа рекомендуется:

```text
Answer.author.url → профиль юриста
```

а профиль юриста размечать как `ProfilePage` + `Person`, если страница соответствует требованиям Google.

Это создаёт корректную сущностную связь:

```text
Question → Answer → Person → ProfilePage
```

### digitalSourceType

В актуальной документации Google QAPage поддерживает `digitalSourceType` для обозначения алгоритмически/LLM-созданного контента.

Если ответ существенно создан автоматикой/LLM и это соответствует реальной истории его создания, такую информацию можно использовать.

Нельзя ставить `digitalSourceType` фиктивно или использовать его как SEO hack.

---

## 18. Профили юристов: ProfilePage вместо декоративной Person-разметки

Для публичного подтверждённого профиля юриста рекомендуется рассмотреть:

```text
ProfilePage
└── mainEntity: Person
```

У `Person` должны быть только реальные публичные данные.

Рекомендуется связывать:

- ответы Q&A;
- статьи;
- профиль;
- области практики;
- проверяемые профессиональные сведения.

Нельзя создавать фиктивные credentials или `sameAs`.

### LocalBusiness / LegalService

Нельзя размечать городскую landing page как `LocalBusiness`, если у платформы/исполнителя нет реального соответствующего бизнеса/офиса по этому адресу.

Schema.org тип `LegalService` допустим как семантическое описание при соответствии фактам, но сам по себе не является гарантией Google rich result или роста позиции.

## 19. Snippet control: data-nosnippet

Неочевидная, но официально поддерживаемая функция Google:

`data-nosnippet` можно использовать для видимых частей страницы, которые не следует использовать при формировании Google snippet.

Подходящие кандидаты в ПравоПоиске:

- повторяющийся legal disclaimer;
- технический текст;
- навигационный boilerplate;
- CTA, который искажает смысл snippet;
- неполезная для выдачи служебная подпись.

Не использовать `data-nosnippet`, чтобы скрывать от Google текст, который создаёт ложное впечатление о содержимом страницы.

Персональные данные должны удаляться/обезличиваться на уровне контента; `data-nosnippet` не является privacy-механизмом.

---

## 20. Яндекс IndexNow

ПравоПоиск должен рассмотреть IndexNow для Яндекса.

Отправлять событие после:

- публикации новой indexable page;
- существенного изменения;
- юридического обновления;
- удаления страницы.

IndexNow ускоряет уведомление поисковика об изменении, но **не гарантирует индексацию**.

Не использовать IndexNow как замену sitemap или нормальной внутренней перелинковке.

---

## 21. Крупный Q&A и crawl budget

Google рекомендует отдельно заниматься crawl budget прежде всего для:

- очень больших сайтов;
- сайтов с 10k+ URL, которые меняются очень часто;
- сайтов с большим количеством `Discovered - currently not indexed`.

ПравоПоиск с крупным Q&A должен мониторить это через Search Console, но не вводить crawl-budget hacks без фактической проблемы.

При наличии проблемы:

- удалять crawl traps;
- не плодить filter/sort URLs;
- держать sitemap актуальным;
- ускорять сервер;
- устранять дубли;
- использовать стабильные canonical URLs;
- не вращать sitemap искусственно;
- не менять robots.txt постоянно ради «перераспределения бюджета».

---

## 22. Core Web Vitals и mobile-first

Целевые хорошие значения Google:

- LCP <= 2.5 s;
- INP < 200 ms;
- CLS < 0.1.

Основной контроль — реальные field data/Search Console, а не только Lighthouse.

Google использует mobile-first indexing.

Поэтому:

- основной индексируемый контент должен быть одинаково доступен mobile и desktop;
- robots metadata должны совпадать;
- structured data должны быть эквивалентны;
- важный основной контент нельзя загружать только после обязательного клика/свайпа/ввода;
- accordion/tabs допустимы, если контент реально присутствует и доступен crawler.

---

## 23. Яндекс: особенности агрегатора юридических услуг

Яндекс официально относит юридические услуги к категории сайтов/агрегаторов услуг.

Для агрегатора Яндекс указывает, в частности:

- предложения должны иметь подтверждаемый источник;
- данные из открытого источника должны быть доступны поставщику для подтверждения/редактирования;
- агрегатор должен публиковать контактные данные юридического лица;
- для сайта услуг важны описание услуги, условия, прайс-лист и способ связи/заказа;
- качество/добросовестность компании может участвовать в дополнительных сигналах Яндекса.

Следовательно, для ПравоПоиска SEO нельзя ограничивать метатегами.

Продуктовая достоверность профилей юристов, реальные цены/условия, возможность связаться и прозрачность оператора сайта — часть поисковой доверительности для Яндекса.

Нельзя создавать:

- фиктивные цены;
- фиктивные офисы;
- фиктивные рейтинги;
- неподтверждённые профили;
- отзывы без реальной основы.

## 24. Проверенные «неочевидные фишки», которые допускаются проектом

Ниже только техники, имеющие официальную поддержку или наблюдаемую legal-практику, согласованную с официальными рекомендациями.

### 24.1 Accurate lastmod вместо искусственной «свежести»

Работает как сигнал об изменении при условии, что дата достоверна.

Для юридического контента связывать `lastmod` с реальным содержательным/legal update.

### 24.2 IndexNow для Яндекса

Отправлять новые/изменённые/удалённые URL сразу после события.

Не гарантирует индекс, но сокращает задержку уведомления.

### 24.3 data-nosnippet для boilerplate

Помогает не отдавать Google повторяющийся disclaimer/CTA как поисковый snippet.

### 24.4 QAPage → author.url → ProfilePage

Корректно связывать ответ с реальным профилем юриста.

Это прямо соответствует актуальным рекомендациям Google QAPage/ProfilePage.

### 24.5 Реальный юридический reviewer и дата проверки

Практика Nolo/FindLaw согласуется с Google Who/How/Why и усиленным trust для чувствительных тем.

### 24.6 Первичные источники в самом контенте

Ссылка на официальный правовой источник должна быть доступна человеку, а не существовать только в скрытых метаданных.

### 24.7 noindex нового/сомнительного UGC до модерации

Google отдельно рекомендует ограничивать индексацию нового/недоверенного UGC как антиспам-механизм.

### 24.8 rel=ugc для пользовательских ссылок

Все пользовательские внешние ссылки должны автоматически получать `ugc` или `ugc nofollow`, если вообще разрешены.

### 24.9 Не делать псевдолокальные страницы

Городская страница должна существовать ради самостоятельной пользы, а не подстановки названия города.

### 24.10 Авторские тематические кластеры

Наблюдаемая практика Justia: Q&A связаны с профилями конкретных юристов, областями практики и историей ответов.

Для ПравоПоиска допустимо строить реальные topical/entity clusters:

```text
юрист
→ его подтверждённые специализации
→ его ответы
→ его статьи/разборы
```

только если связи отражают фактические данные.

## 25. Что не делать

Запрещается внедрять без отдельного подтверждённого основания:

- `llms.txt` «для Google AI SEO»;
- автоматический AI-рерайт тысяч страниц ради уникальности;
- keyword stuffing;
- скрытый текст;
- массовые городские doorway pages;
- искусственные отзывы;
- фиктивные авторы/эксперты;
- фиктивные даты обновления;
- создание FAQ ради количества;
- создание JSON-LD ради score;
- массовое удаление старого полезного контента ради «freshness»;
- canonical как способ скрыть проблему originality;
- robots.txt как гарантированный способ убрать HTML URL из индекса;
- `acceptedAnswer` = первый/последний ответ без механизма принятия;
- копирование чужого Q&A с минимальным рерайтом;
- генерация десятков страниц под один intent.

## 26. Что требуется изменить в текущей реализации

На дату 2026-09-29 текущий код проекта содержит правила, которые нужно считать устаревшими относительно этого документа.

### Удалить как hard SEO gates

- `seoScore >= 70` как обязательное условие индексации;
- `seoText >= 1500` как критерий качества;
- `faqCount >= 3` как общий индексный gate;
- обязательный FAQ для article/city/service/listing pages;
- наличие любого JSON-LD как часть SEO score;
- CTA как часть SEO score;
- фиксированный minimum internal links;
- фиксированный text length как универсальный SEO-фактор.

Часть этих значений может остаться как внутренняя редакционная диагностика, но не должна автоматически означать `index/noindex`.

### Исправить

- `?page=N`: не блокировать настоящую пагинацию общим `noindex`;
- pagination pages должны иметь self-canonical;
- filters/sort отделить от pagination;
- убрать конфликт `robots Disallow` + ожидание `noindex`;
- sitemap Q&A должен использовать полную специальную query, а не paginated repository method;
- Q&A sitemap дробить по лимитам;
- добавить точный `lastmod`;
- убрать blanket `changefreq=weekly`;
- `acceptedAnswer` ставить только реальному accepted answer;
- для обычных ответов использовать `suggestedAnswer`;
- добавить `ProfilePage` для подходящих публичных профилей юристов;
- удалить `SearchAction` из `WebSite`, если он используется только ради Google Sitelinks Search Box;
- `FAQPage` убрать из обязательного Google SEO flow;
- не размечать `LocalBusiness` без реального локального бизнеса/офиса.

## 27. Автоматический SEO FAIL

Страница не проходит SEO acceptance, если:

- blocked by robots, но мы рассчитываем на `noindex`;
- canonical конфликтует с sitemap/internal links;
- indexable page является semantic duplicate без самостоятельной ценности;
- mass/programmatic page отличается только подстановкой города/ключа;
- imported Q&A не прошёл originality/legal gates;
- отсутствующая страница возвращает 200 и выглядит как empty/soft 404;
- structured data описывает невидимый или несуществующий контент;
- `acceptedAnswer` назначен без механизма принятия;
- публичная lawyer/business schema содержит выдуманные данные;
- sitemap содержит noindex/redirect/404/duplicate;
- mobile версия теряет основной контент;
- страница юридически устарела, но показывает себя как актуально проверенную;
- пользовательские внешние ссылки могут массово публиковаться без moderation/UGC protection.

---

## 28. PASS

SEO acceptance = PASS, когда:

- URL технически доступен и имеет корректный HTTP status;
- страница обладает самостоятельной пользовательской ценностью;
- canonical непротиворечив;
- robots/indexing rules непротиворечивы;
- страница не является unresolved duplicate/doorway;
- основной контент доступен mobile-first crawler;
- юридически значимый контент прошёл соответствующую проверку;
- sitemap содержит только допустимую canonical версию;
- structured data, если есть, соответствует видимому контенту;
- Q&A дополнительно прошёл `QNA_CONTENT_RULES.md`;
- нет искусственных SEO-порогов, которые подменяют реальное качество.
